Scalability Guide

How many of each component to run, how they partition work across AMQP, how to spot bottlenecks, and worked examples from single-SDR to multi-node cluster deployments.

Per-Component Scaling Rules

Component Scale with Rule of thumb Max per host Notes
SdrResourceManager Hosts with USB SDRs 1 per physical host 1 Arbitrates all USB SDR devices on one machine. Run one per node in a multi-node cluster. Stateless — restart is safe.
AcquisitionApp SDR devices / frequency bands 1 per SDR channel 8–12 (CPU bound) One instance owns one SDR + one frequency band. To cover multiple bands on a wideband SDR, run one instance per band and time-share via SdrResourceManager task scheduling.
DemodApp Active protocols / signal volume 1 per 4–6 active demodulators 4–6 (per 12-core CPU) Each instance handles a subset of protocols. Partition by category: one instance for aviation (ADS-B/ACARS/VDL2), one for maritime (AIS/DSC), one for land mobile (P25/DMR). AMQP anycast balances load automatically.
AnalysisApp GPUs / classification throughput 1 per GPU 1 per GPU (or N CPU instances) ONNX Runtime pins to a single device. For CPU-only: add instances until CPU saturation — each takes ~65% of one core at continuous load. Multiple instances consume the same AMQP queue competitively (anycast).
SpeechApp Simultaneous P25 voice channels 1 per 2–3 concurrent voice streams 4 GPU / 2 CPU whisper.cpp processes one audio segment at a time per instance. A busy trunked system may have 10+ simultaneous voice grants. Scale instances until queue depth stays below 2× realtime. GPU realtime factor is 0.12× (very fast).
DfApp Coherent SDR pairs 1 per 2-channel coherent SDR pair N/A (hardware limited) MUSIC direction finding requires phase-coherent dual Rx (USRP B210 or two synchronized PlutoSDRs). One DfApp instance per coherent hardware pair. Cannot parallelize beyond hardware.
Apache Artemis Message throughput 1 broker for up to ~50k msg/s 1 (add federation for multi-site) Single Artemis broker handles typical deployments comfortably. For multi-site (geographically distributed SDRs) use Artemis federation to bridge brokers. Each site runs its own broker.
PostgreSQL Alert write rate 1 instance handles all writes 1 primary (add read replicas for dashboards) Alert insert rate is low (tens/minute). PostgreSQL is not a bottleneck. Add a read replica only if Grafana/dashboard queries slow down the primary.

AMQP Address & Routing

All components communicate exclusively via Apache Artemis AMQP 1.0. Multiple instances of the same component share a queue — Artemis distributes messages round-robin (anycast). This means scaling is usually a matter of adding more instances without any configuration change.

AMQP AddressProducerConsumer(s)RoutingNotes
iq.frames.{band} AcquisitionApp DemodApp, AnalysisApp Multicast Each AcquisitionApp publishes to a band-specific address. All consumers that subscribe receive a copy.
classify.requests AcquisitionApp AnalysisApp ×N Anycast All AnalysisApp instances compete on one queue. Artemis distributes round-robin — add instances to linearly scale throughput.
demod.results DemodApp signal_logger, AlertConsumer Multicast Results fan out to all subscribers. Logger writes to PostgreSQL; AlertConsumer evaluates threat conditions.
voice.frames DemodApp (P25) SpeechApp ×N Anycast P25 voice segments queued and consumed by whichever SpeechApp instance is free. Scale instances to keep queue depth near 0.
rf.alerts AlertConsumer, DemodApp AlertStore (PostgreSQL) Anycast Low volume. Single consumer writes to the rf_alerts table. AlertStore is not a scaling concern.
sdr.resource.requests AcquisitionApp SdrResourceManager Anycast RPC-style request/reply for SDR lease acquisition and release. One SdrRM per host holds all device locks.
df.estimates DfApp signal_logger Multicast Direction-finding bearing estimates published for each detection event. Low volume, not a scaling concern.
Anycast = free horizontal scaling. To double AnalysisApp throughput, start a second instance pointed at the same broker — no config changes needed. Artemis splits the classify.requests queue between both consumers automatically. Same applies to DemodApp and SpeechApp.

Bottleneck Detection

🔵 AcquisitionApp overloaded

Symptoms: IQ frame timestamps lag wall clock by >100 ms. Artemis queue depth for iq.frames.* grows unboundedly. CPU on AcquisitionApp process > 90%.
Fix: add another SDR + AcquisitionApp instance on a different frequency band. Reduce dwell_ms or increase FFT stride. Check USB bus bandwidth — multiple RTL-SDRs on the same USB controller share 480 Mbps.

🟣 AnalysisApp queue backing up

Symptoms: classify.requests queue depth > 500. Classification results arrive seconds after IQ capture. GPU utilization < 60% (under-batching).
Fix: increase batch_size in analysis.xml (up to 256 on 8 GB VRAM). If GPU is already saturated, add a second GPU + AnalysisApp instance — Artemis load-balances automatically.

🟢 DemodApp dropping frames

Symptoms: AIS or ADS-B decode count drops during high-traffic periods. Demod process CPU > 80%. Log shows frame dropped — demod busy.
Fix: split protocols across two DemodApp instances (e.g., aviation in one, maritime in another). Each instance subscribes only to the iq.frames.* addresses it needs — configure protocols list in demod.xml.

🟠 SpeechApp transcript lag

Symptoms: voice.frames queue depth grows during active P25 traffic. Transcripts arrive >10 s after audio capture. whisper.cpp realtime factor degrades.
Fix: add SpeechApp instances — each consumes from the same anycast queue. On CPU: each instance uses ~85% of one core. On GPU: 4 instances share one GPU comfortably (0.12× realtime factor per instance). Start with 1 instance per 3 concurrent voice grants.

🔴 Artemis broker memory pressure

Symptoms: Artemis heap usage > 80%. Messages start spilling to disk (address paging). Latency spikes. Artemis console shows high queue depth on multiple addresses.
Fix: identify slow consumers with artemis queue stat. Scale the slow consumer. For multi-site: use Artemis federation — each site processes its own traffic locally and only forwards alerts to the central node.

⚪ PostgreSQL write latency

Symptoms: signal_logger log shows INSERT latency > 50 ms. AlertStore commit times spike. Postgres CPU > 80% (rare — usually means too many concurrent connections).
Fix: PostgreSQL is almost never the bottleneck at SDR scales. If it is, add a connection pooler (PgBouncer). Consider partitioning the rf_signals table by day if it exceeds 100M rows. Add indexes on timestamp and frequency_hz.

Note on SdrResourceManager and multi-host deployments: SdrResourceManager must run on the same physical host as the USB SDR devices — it cannot proxy USB devices over a network. In a multi-node cluster, run one SdrResourceManager per node that has SDRs attached. All other components (DemodApp, AnalysisApp, SpeechApp) can run on any node that has network access to the AMQP broker.
