Architecture

The stack is built around a single design rule: all inter-component communication goes through Apache ActiveMQ Artemis over AMQP 1.0. No component calls another directly. Every piece of data — IQ snapshots, detections, classification results, decoded bits, bearings — travels as a JSON message on a named topic. This means any component can be swapped, scaled, or removed without touching any other component's code.

Quick Start

1

Clone SdrScripts

git clone https://github.com/OpenRFStack/SdrScripts
cd SdrScripts
2

Configure your SDR device

Edit hw-test/devices-direct.xml with your SoapySDR driver string. The caps block tells the scheduler what the device can do — if a task requests a frequency outside this range the Resource Manager will reject it before even touching the hardware.

<device>
  <id>sdr-0</id>
  <driver>rtlsdr</driver>        <!-- hackrf / lime / uhd / plutosdr / airspyhf / sdrplay -->
  <caps>
    <freq_min_hz>500000</freq_min_hz>
    <freq_max_hz>1700000000</freq_max_hz>
    <sample_rate_max_sps>3200000</sample_rate_max_sps>
    <num_rx>1</num_rx>
  </caps>
</device>

For a multi-device setup add additional <device> blocks. The Resource Manager will schedule across all of them and handle independent-LO or shared-LO allocation automatically.

3

Start the stack

# Acquisition + broker only — lightest config
./scan.sh --hw --no-analysis

# With classification (36-class AMR)
./scan.sh --hw

# Add demodulation (all 25+ protocol decoders)
./scan.sh --hw --demod

# Full pipeline — classify, demodulate, direction-find
./scan.sh --hw --demod --df

scan.sh pulls container images, starts Artemis, starts all selected components in order, and purges stale AMQP task queues from any previous run. All containers are managed by Podman; no Docker daemon required.

4

Query live results

-- All signals seen in the last 10 minutes
SELECT last_seen, round(freq_mhz::numeric,4) AS freq_mhz,
       round(bw_khz::numeric,1) AS bw_khz, modulation,
       round(hyp_conf::numeric,2) AS conf, hits
FROM recent_signals
ORDER BY last_seen DESC;

-- P25 channel activity with encryption info
SELECT role, round(freq_mhz::numeric,4) AS freq_mhz,
       talk_group, encrypted, alg_name, key_id, grant_count, last_seen
FROM p25_site_channels
ORDER BY role, freq_mhz;

-- Recent voice transcriptions
SELECT ts_utc, round(freq_hz/1e6::numeric,4) AS freq_mhz,
       modulation, language, text
FROM transcripts
ORDER BY ts_ms DESC LIMIT 20;

Multi-device scheduling

Configure multiple devices in devices-direct.xml. The Resource Manager assigns tasks to devices based on frequency range, available bandwidth, and current load. A task requesting 462 MHz will be assigned to whichever device covers that range and has capacity — the requesting component never needs to know which physical hardware was used.

GPU recommendations

For inference only (no training), any recent mid-range GPU works well. The ML inference load is modest:

  • AnalysisApp fast path: ~5 ms / signal on ONNX CUDA
  • SpeechApp Whisper base.en: ~25× real-time on a modern GPU
  • Minimum GPU: GTX 1060 6GB or equivalent (runs both comfortably)
  • Recommended: RTX 3060 12GB or better for headroom with large Whisper models

The stack also runs fully on CPU. Use int8-quantised ONNX and Whisper tiny.en for embedded / Raspberry Pi / Jetson deployments.

Resource Manager

⇗ GitHub C++20 200+ tests ✓

The central hardware broker. Every component that needs IQ samples submits a TaskRequest over AMQP; the Resource Manager schedules it, allocates a UDP port from the pool, programs the SDR hardware via SoapySDR, and streams CF32 IQ to the requester's UDP socket. No component ever touches hardware directly.

Task scheduling modes

Priority preemption

Three-tier rank: Acquisition (1) < Classification (2) < Direction Finding (3). A higher-rank task preempts a lower-rank task: the lower-rank task is notified, its port is reclaimed, and the SDR is retuned. The preempted task can be re-submitted after the higher-priority task completes.

Shared-LO fan-out

Two tasks at the same centre frequency share a single hardware channel via sub-band decomposition. The second subscriber pays zero retune cost and begins receiving IQ immediately. Both tasks see the same samples on independent UDP sockets.

Independent-LO

On multi-RX devices (USRP B210, LimeSDR, BladeRF) tasks at different frequencies run truly simultaneously on separate RF chains. Both get their full requested bandwidth with no sharing overhead.

Combined-window

When a second task falls within the device's instantaneous bandwidth, the Resource Manager recentres to a wider frequency covering both and extracts each task's sub-band. Neither task loses samples during the transition.

Task lifecycle and state machine

Each task passes through: PENDING → RUNNING → COMPLETED (or PREEMPTED / FAILED). State transitions are atomically managed to prevent double-deactivation races. The port pool uses atomic claims — a port in state ASSIGNED cannot be double-released even if two threads reach the cleanup path simultaneously.

AcquisitionApp

⇗ GitHub C++20 64 tests ✓

Continuous spectrum scanner. One process per host — manages all SDR devices on that machine. At startup it queries SdrResourceManager for the number of online devices, then auto-splits the configured frequency bands into equal slices so every device covers a unique non-overlapping range. Submits frequency-sweep tasks to SdrRM, receives CF32 IQ over UDP, runs a four-stage detection pipeline, and publishes every confirmed detection to rf.detections. Also handles P25 voice channel following when grants arrive on rf.p25.grants.

Multi-device auto-split

Configure one or more <band> entries in scanner.xml. On startup AcquisitionApp sends a HEALTH_QUERY to SdrRM and reads controller.num_devices_online. If devices > bands, each band is subdivided into equal frequency slices — one per device — so the full spectrum is covered with no overlap and no manual device assignment:

Bands configuredDevices onlineResult
14Band split into 4 equal slices → 4 scanners, 4 devices
24Each band split into 2 slices → 4 scanners, 4 devices
34Band 0 → 2 slices, bands 1–2 → 1 slice each → 4 scanners
441:1, no split → 4 scanners, 4 devices

Sweep resume after preemption

Each scanner tracks resume_hz_ — updated on every received UDP packet. When a higher-rank task (AnalysisApp rank 2, DfApp rank 3) preempts the scan, streaming stops and the scanner re-submits. The new task's dwell entry list starts from resume_hz_, wraps through stop_hz, then continues from start_hz to resume_hz_ — guaranteeing every frequency is visited exactly once per task regardless of where the previous task was interrupted. No frequency starves.

Detection pipeline

📊
Welch averaging

Multiple 50%-overlapping Blackman-Harris windowed FFT frames averaged in linear (not dB) power. Reduces noise variance by ~18 dB vs single-shot FFT at 8× averaging, revealing signals near the noise floor.

→
🎯
CA-CFAR

Cell-Averaging CFAR with O(N) prefix-sum implementation. Default: 8 guard cells + 32 reference cells per side. Threshold = noise_estimate × 10^(threshold_db/10). Adapts to local noise density automatically.

→
🔁
Persistence filter

A bin must exceed the CFAR threshold in ≥2 consecutive sweeps before it emits a detection. Strong signals (PAPR ≥15 dB) bypass this and emit immediately, preventing latency on impulsive emitters.

→
📍
Sub-bin interpolation

3-point parabolic fit on the FFT peak and its two neighbors. Achieves ±1–2 kHz centre-frequency accuracy regardless of FFT bin width without reducing bin size.

CA-CFAR parameter tuning

Key parameters in scanner.xml:

ParameterDefaultEffect
cfar_guard_cells8Cells excluded around the test cell. Increase if signal is wide (e.g. FM broadcast leaks into guard region).
cfar_ref_cells32Reference window size. More cells = better noise estimate but slower CFAR per sweep.
threshold_db6.0dB above estimated noise floor to declare a detection. Lower = more sensitivity but higher false alarm rate.
persistence_sweeps2Consecutive sweeps a bin must be above threshold before emitting. Increase to suppress transient interference.
high_papr_db15.0Signals with PAPR above this bypass the persistence filter and emit on first detection.

P25 voice channel following

The P25GrantConsumer thread subscribes to rf.p25.grants. When a grant arrives it queues a NARROWBAND task request at rank 3 (highest priority) for the voice channel frequency. Captured IQ is published to rf.detections with scanner_id set to scanner-0-tg{talk_group}, allowing DemodApp and SpeechApp to associate the audio with a specific talk group.

AnalysisApp — Signal Classification

⇗ GitHub C++20 33 tests ✓

Automatic modulation recognition (AMR) service. Classifies every detected signal into one of 47 modulation and protocol classes using a two-path ONNX pipeline. The 47-class RadioResNet achieves val_acc = 0.748 (best epoch 38/40, 40-epoch training run). Includes 11 new protocol-specific classes: FLEX, MDC-1200, DTMF, EAS/SAME, RTTY, P25 Phase 2, ADS-B, DSC, NAVTEX, VDL Mode 2, PSK31.

Fast path — ~5 ms

A 36-class RadioResNet runs directly on the 1024-sample IQ snapshot embedded in every RF_DETECTION message. No SDR re-acquisition. Fires and publishes when confidence ≥ 0.75.

The model was trained on 922k synthetic samples covering −10 to +30 dB SNR with realistic hardware impairments: IQ imbalance (±0.5 dB / 0.5°), DC offset, phase noise (−80 dBc/Hz), AWGN, and multipath (1–3 tap Rayleigh fading, max delay 5% symbol period).

Slow path — ~80 ms

Triggered when fast-path confidence < 0.75. Requests a 65k-sample NARROWBAND capture and computes:

  • 4th-order cumulants C42 and C40 — distinguish modulation order within a family (BPSK vs QPSK vs 8PSK)
  • OFDM cyclic prefix ratio — identifies OFDM vs single-carrier
  • FM peak deviation — separates WB (±75 kHz) from NB FM (±2.5–5 kHz)
  • Linear chirp rate — detects CSS/LFM spread-spectrum
  • PAPR and spectral flatness — noise vs modulated signal

Rule engine and ONNX inference run in parallel; the higher-confidence result is published.

DemodApp — Demodulation

⇗ GitHub C++20 CI ✓

Demodulates classified RF signals into decoded content — audio PCM, bit streams, or parsed text. Subscribes to rf.analysis, requests IQ via NARROWBAND tasks for signals above the confidence threshold, and publishes decoded output to rf.demod.

All physical-layer demodulation uses liquid-dsp: FM frequency discriminator (freqdem), RRC-matched symbol synchroniser (symsync_cccf), Gaussian filter (GMSK), Costas-loop carrier recovery (PSK/QAM), and 4-level slicer (4FSK). A shared IDemod interface means adding a new protocol requires only one new class with a single process(iq, sr, center_freq, timestamp) method.

P25 control channel decoder

The P25Monitor continuously decodes the Phase 1 control channel. The signal chain is: CA-CFAR detection → NARROWBAND IQ capture → C4FM 4FSK demodulation (4800 sym/s, ±600 / ±1800 Hz deviation) → dibit extraction → TSBK frame sync (0x7BF5) → TSBK opcode dispatch → AMQP publish.

Voice channel HDUs (Header Data Unit) are decoded separately: the ALGID byte at bits 28–35 and KID at bits 36–51 are extracted and stored alongside each grant. This enables tracking of encrypted talk groups without decrypting any content.

DfApp — Direction Finding

⇗ GitHub C++20 CI ✓

Estimates the bearing (direction of arrival) of detected RF signals using the MUSIC algorithm (MUltiple SIgnal Classification). Operates on IQ snapshots from multiple receivers that share a common oscillator reference — phase differences between antenna elements are then purely geometric.

MUSIC algorithm

  1. Receive M IQ snapshot vectors (one per antenna element, same signal, different spatial positions)
  2. Build the M×N complex sample matrix X (M antennas, N time samples each)
  3. Form the spatial covariance matrix R = XXH / N
  4. Eigendecompose R → signal subspace ES (D eigenvectors) and noise subspace EN (M−D eigenvectors)
  5. Compute the steering vector a(θ) = [1, ej2πd sinθ/λ, …] for each candidate azimuth θ at 0.5° resolution
  6. Evaluate the MUSIC pseudospectrum: P(θ) = 1 / ‖ ENH a(θ) ‖²
  7. Return the global peak azimuth and its prominence (peak / mean) as the confidence score
PMUSIC(θ) = 1 / ‖ ENH a(θ) ‖²

Array geometry

DfApp supports Uniform Circular Array (UCA) geometry. The steering vector is computed at runtime from the array radius, number of elements, element positions, and carrier wavelength. The default configuration is a 5-element UCA with element spacing d = λ/2 at the signal frequency. Wavelength is computed from the signal's detected centre frequency so the same array works across VHF/UHF.

Phase coherence requirements

All receivers must share a common LO reference — without coherence, phase offsets between receivers are random and bearing estimation fails completely. Options:

  • GPS-disciplined oscillator: Best absolute phase accuracy. Each receiver locked to a GPS 10 MHz reference. Required for multi-site DF.
  • Hardwired reference: Single LO distributed to all receivers via coax splitter. Works for collocated arrays (<10 m separation).
  • Coherent multi-channel device: USRP B210 or BladeRF with dual RX — built-in phase coherence, no external reference required.

The aggregation window (default 5 s, configurable) holds incoming snapshots until all M elements have reported for the same signal, then triggers MUSIC computation.

SpeechApp — Voice Transcription

⇗ GitHub C++20

Passive subscriber to rf.demod. Two-stage pipeline: an energy VAD gates Whisper inference (skipping silence and digital bursts in <1 ms), then whisper.cpp transcribes detected speech. No Python, no PyTorch at runtime — pure C++ GGML inference. Transcriptions stored in SQLite with metadata and appended to a rolling daily text log.

EnergyVad — <1 ms

RMS energy computed over a sliding window. If the window RMS in dBFS is below a configurable threshold the audio is discarded before Whisper is even called. Threshold is set to pass voice-band energy (400 Hz–3.4 kHz) while rejecting broadband noise, DTMF tones, FSK bursts, PSK31, and other digital signals that don't contain intelligible speech.

In tests, VAD correctly detects speech at p=1.000 at SNR 5 dB even through 50 Hz AC hum and 150 ms multipath fades.

whisper.cpp integration

GGML-quantised Whisper model loaded at startup. Supports int8 CPU inference and float16 CUDA inference. The WhisperTranscriber class wraps the C API: whisper_init_from_file(), whisper_full(), segment extraction.

Input PCM (any sample rate) is linearly interpolated to 16 kHz before inference via the Resampler class. Segment timestamps are stored alongside the transcript text for later search and correlation with detection records.

Threat Detection

The stack includes passive RF threat detection across two layers. All alerts are stored in the rf_alerts PostgreSQL table and queryable via SELECT * FROM recent_alerts;. Every feature is disabled by default and individually controlled in config files.

GPS jamming and spoofing (AcquisitionApp)

GpsMonitor periodically captures 100 ms of IQ at L1 (1575.42 MHz), L2 (1227.60 MHz), and L5 (1176.45 MHz). It maintains an exponential moving-average noise baseline per band and classifies any anomaly:

Jamming — GPS_JAMMING

Power exceeds the EMA baseline by ≥ 20 dB (configurable). Catches broadband noise jammers, CW tone jammers, and sweep jammers. Severity: HIGH (<40 dB delta) or CRITICAL (≥40 dB).

Spoofing — GPS_SPOOFING

A BPSK-shaped signal (~0.5–5 MHz BW) at a GPS carrier at detectable power (> −110 dBm). Real GPS signals are always ~20 dB below the noise floor — any detectable signal at L1/L2/L5 is suspicious. Severity: CRITICAL.

Content-layer validators (DemodApp)

Each demodulator runs an in-process validator after decoding. Anomalies set DemodResult::alert_json; DemodRouter forwards them to rf.alerts AMQP, which AcquisitionApp persists to the database.

SdrSdk

⇗ GitHub C++20

C++ client library for writing SDR applications without touching AMQP internals, raw UDP sockets, or task scheduling. Physical quantities use the Au units library 0.5.1 — frequency, bandwidth, and duration parameters are type-checked at compile time, preventing unit mismatches that would otherwise be silent runtime bugs.

Narrowband capture example

#include <sdrsdk/sdrsdk.hpp>
#include <au/units/hertz.hh>
#include <au/units/seconds.hh>

sdr::SdrClient client("amqp://localhost:5672");
client.connect();

// Submit a 3-second NARROWBAND capture at 462.5 MHz, 12.5 kHz BW
auto resp = client.narrowband(
    au::hertz(462.5e6),   // centre frequency
    au::hertz(12.5e3),    // bandwidth
    au::hertz(48e3),      // sample rate
    au::seconds(3.0));    // duration

if (resp.status != sdr::TaskStatus::Accepted) {
    std::cerr << "Task rejected: " << resp.reason << "\n";
    return;
}

// Receive IQ via the assigned UDP port
sdr::IqStream stream(resp.streams[0].udp_port);
auto iq = stream.collect_complex_for(au::seconds(3.0));
client.stop(resp.task_id);

// Spectrum analysis
sdr::Spectrum spec(4096);
auto signals = spec.analyse(iq, au::hertz(462.5e6), au::hertz(48e3));
for (auto& s : signals)
    std::cout << s.freq.in(au::mega(au::hertz)) << " MHz  "
              << s.power_db << " dB  " << s.type << "\n";

// Multi-step scan across the GMRS/FRS band

Multi-Site Direction Finding

Direction finding requires phase-coherent IQ from multiple antenna elements. The MUSIC algorithm measures phase differences between antennas to compute bearing — this only works if all receivers share the same oscillator reference.

Hardware options for coherent reception

USRP B210 (built-in coherence)

Dual RX on a single board. Both channels are inherently phase-coherent — no external reference needed. Best for 2-element arrays. Multiple B210s require GPS-DO or shared reference.

LimeSDR / BladeRF (dual-RX)

Same as B210 — dual coherent RX per board. LimeSDR Mini 2.0 supports 2 channels. Multiple boards require external reference.

GPS-Disciplined Oscillator (GPSDO)

Best absolute accuracy. Each USRP or HackRF locked to a shared GPS 10 MHz reference via SMA splitter. Required for multi-host DF where receivers are separated by more than a cable run.

Hardwired LO reference

Single oscillator → coax splitter → all receivers. Works for collocated arrays (<10 m separation). Low cost — any stable 10 MHz source works.

Frequently Asked Questions

Why is classification slow on the first signal?

ONNX Runtime loads and JIT-compiles the model on first inference. With CUDA, this takes 2–5 seconds. Subsequent inferences are ~5 ms. The warm-up cost is a one-time startup penalty — it goes away after the first signal is classified. With TensorRT enabled (<use_tensorrt>true</use_tensorrt>), a compiled engine is cached to disk so even cold starts are fast after the first ever run.

RTL-SDR tops out at ~1.7 GHz — can it receive GPS (1575 MHz)?

Marginally. The RTL-SDR Blog v3/v4 has a nominal max of 1.7 GHz but reception quality degrades above ~1.5 GHz. GPS L1 at 1575.42 MHz is theoretically reachable but sensitivity is very poor — you'd need a GPS patch antenna with LNA and a clear sky view. For reliable GPS monitoring use a HackRF One (up to 6 GHz) or USRP B210. For ADS-B at 1090 MHz, the RTL-SDR works excellently.

Why is QAM64 accuracy only ~7%?

QAM64 sits between QAM32 (32 points) and QAM256 (256 points) in constellation density. At the SNR levels in the training data, all three look nearly identical — the model can't reliably distinguish them. The 512-sample input window captures only a few symbol periods, and at low SNR the constellation becomes noise. The v2 model addresses this with 4× QAM oversampling, 1024-sample windows (more symbol statistics), and a wider network (256 channels vs 128). Expected improvement: 7% → ~40%.

How many simultaneous SDRs can I use?

Unlimited — the Resource Manager supports any number of SoapySDR devices configured in devices-direct.xml. Each device runs a dedicated IQ streaming thread. The scheduler automatically distributes tasks across devices based on frequency range, bandwidth, and current load. In practice, system USB bandwidth limits RTL-SDR to 3–4 per USB controller; USRP/HackRF/LimeSDR over gigabit ethernet scale better.

What's the difference between the fast path and slow path?

The fast path (~5 ms) runs ONNX inference on the 1024-sample IQ snapshot embedded in every RF_DETECTION message — no additional SDR acquisition needed. The slow path (~80 ms) is triggered when fast-path confidence is below the threshold (default 0.75). It requests a fresh 65k-sample NARROWBAND capture, extracts features (cumulants, FM deviation, OFDM CP ratio, PAPR), and runs both a rule engine and ONNX in parallel. The higher-confidence result is published.

Do I need a GPU to run the stack?

No — everything runs on CPU. GPU accelerates three things: ONNX inference in AnalysisApp (~5 ms GPU vs ~30–100 ms CPU), Whisper transcription in SpeechApp (~40 ms GPU vs ~400 ms CPU), and ML training. For a deployment that just detects and classifies signals (no transcription), a modern 4-core CPU handles the load comfortably. If you use --demod with SpeechApp, GPU is strongly recommended for real-time transcription.

Which Whisper model should I use for live voice monitoring?

For English-only real-time use: base.en (145 MB) is the tested baseline and runs at ~7× real-time on CPU / ~25× on GPU. For maximum accuracy: medium (1.5 GB) on a GPU. For an embedded/Pi deployment: tiny.en (75 MB) at ~15× real-time on CPU. The accuracy difference between base and medium is most visible at SNR 5–10 dB where base.en starts making errors.

Why does the full sweep take 7+ seconds?

At 20 MSPS with 0.8 usable bandwidth fraction, each sweep step covers 16 MHz. To sweep 70 MHz → 1 GHz (930 MHz span) requires ≈58 steps. Each step dwells for 4096/20MHz = 0.2 ms of IQ, but the SDR retune + settle time adds ~100 ms per step. Result: 58 × ~130 ms ≈ 7.5 seconds. Reduce the span or increase sample rate to speed up. For fast detection of known frequencies, use targeted NARROWBAND tasks instead of a sweep.

How do I find my local P25 control channel?

The RadioReference database lists all licensed P25 systems with control channel frequencies. Look up your county or city. Alternatively, run a spectrum scan and look for a 12.5 kHz flat-top signal near 851–869 MHz (800 MHz P25) or 769–806 MHz (700 MHz) that is always on — P25 control channels are continuous, unlike voice channels which are intermittent. Query SELECT freq_mhz, hits FROM recent_signals WHERE bw_khz BETWEEN 10 AND 15 ORDER BY hits DESC to find candidates.

Why would I run multiple AcquisitionApp instances?

Each instance drives one sweep plan — one set of frequencies, one scan pattern, one scanner_id. Multiple instances are useful in four situations:

  • Multiple physical SDRs — one RTL-SDR covers 70 MHz–1.7 GHz, a HackRF covers 1–6 GHz. Two instances, each submitting tasks for their device. The Resource Manager assigns tasks to the right hardware automatically based on frequency range.
  • Geographic distribution — one instance on a hilltop (remote site over ethernet), another at the base station. Both publish detections to the same AMQP broker and PostgreSQL, distinguished by scanner_id.
  • Parallel P25 + wideband sweep — one instance dedicated to following P25 voice grants (high-priority narrowband tasks), another doing the broad spectrum sweep. Prevents the sweep being interrupted every time a P25 grant fires.
  • Band splitting for speed — sweeping 70 MHz–1 GHz takes ~7.5 s. Split across two instances and two SDRs (70–500 MHz / 500 MHz–1 GHz) and full coverage completes in ~3.5 s.

All instances share the same Resource Manager, AMQP broker, AnalysisApp, DemodApp, and database. Every detection appears in the same signals table, labelled by scanner_id.

-- See which scanner detected each signal
SELECT scanner_id, count(*), round(avg(snr_db)::numeric,1) AS avg_snr
FROM signals
WHERE last_seen > now() - INTERVAL '1 hour'
GROUP BY scanner_id;

Contributing — Adding a Demodulator

Adding a new protocol to DemodApp requires three files and one routing entry. The IDemod interface is minimal — one method, one return type.

1

Create the header

// include/demod/MyProtoDemod.hpp
#pragma once
#include "demod/IDemod.hpp"
namespace demod {
class MyProtoDemod : public IDemod {
public:
    DemodResult process(const std::vector<std::complex<float>>& iq,
                        au::QuantityD<au::Hertz>   sr,
                        au::QuantityD<au::Hertz>   center_freq,
                        au::QuantityD<au::Seconds> timestamp) override;
};
} // namespace demod
2

Implement in the .cpp

// src/demod/MyProtoDemod.cpp
#include "demod/MyProtoDemod.hpp"
#include <liquid/liquid.h>  // use freqdem, symsync_rrrf, modemcf, etc.
#include <spdlog/spdlog.h>

namespace demod {
DemodResult MyProtoDemod::process(const std::vector<std::complex<float>>& iq,
                                   au::QuantityD<au::Hertz> sr, ...) {
    DemodResult r;
    r.type       = DemodClass::Bits;   // or Audio / RawIq
    r.modulation = "MY_PROTO";
    // ... demodulate using liquid-dsp primitives ...
    // Optionally set r.alert_json for threat detection
    return r;
}
} // namespace demod
3

Add to DemodRouter

// src/DemodRouter.cpp — add two things:

// 1. Include at top
#include "demod/MyProtoDemod.hpp"

// 2. Add to paramsFor() — return fetch parameters
if (mod == "MY_PROTO") {
    return {au::hertz(50'000.0), bw,
            cfg_.engine.digital_duration,
            DemodClass::Bits, 2, au::hertz(0.0)};
}

// 3. Add to route() dispatch switch
case "MY_PROTO": result = MyProtoDemod{}.process(iq, actual_sr, center_freq, ts); break;
4

Add to CMakeLists.txt and write a test

# CMakeLists.txt — add to demod_lib sources
add_library(demod_lib STATIC
    ...
    src/demod/MyProtoDemod.cpp
)

Add a test in tests/test_protocol_demods.cpp using a spec-accurate synthetic waveform. Tests run in CI via podman build --target test.

Adding an ML training class

To include the new protocol in the 47-class model, add a generator function in tools/ml/generate_v3.py and register it in the _gen_one() dispatch. The generator takes (length, rng) and returns a complex64 numpy array of IQ samples at the reference sample rate (200 kHz). Realistic impairments (IQ imbalance, AWGN, freq offset) are applied automatically by the training pipeline.
