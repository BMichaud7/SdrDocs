Pre-built Container Images

Fastest path to production. Pre-built images for both node types are published to GitHub Container Registry (ghcr.io/openrfstack). No source checkout or compilation required — the entrypoint downloads SDR binaries from GitHub Releases on first boot and self-updates on restart.
1

Authenticate to GHCR

Images are private. Pull requires a GitHub PAT with read:packages scope. Store the token somewhere safe (e.g. ~/.config/openrfstack/ghcr_token, chmod 600) then log in:

cat ~/.config/openrfstack/ghcr_token | sudo podman login ghcr.io -u YOUR_GH_USERNAME --password-stdin
# Works identically with docker login ghcr.io
2

Run sdr-node (fixed-site deployment)

Runs SdrResourceManager, AcquisitionApp, DemodApp, AnalysisApp, SpeechApp, and all infrastructure (Artemis, PostgreSQL) inside an embedded k3s cluster. k3s API listens on port 6443.

sudo podman run -d \
  --name sdr-node \
  --network host \
  --privileged \
  -v sdr-k3s:/var/lib/rancher/k3s \
  -v /dev/bus/usb:/dev/bus/usb \
  ghcr.io/openrfstack/openrfstack-node:latest

# Follow startup logs:
sudo podman logs -f sdr-node
USB SDR access requires --privileged and host udev rules set before container start. See Common Issues → SoapySDR device not found.
3

Run sdr-mobile (drone / embedded)

Lightweight variant: SdrResourceManager, AcquisitionApp, and GpsApp only — no AnalysisApp or DemodApp. Designed to coexist on the same host as sdr-node; its k3s API uses port 6444 by default.

sudo podman run -d \
  --name sdr-mobile \
  --network host \
  --privileged \
  -v sdr-mobile-k3s:/var/lib/rancher/k3s \
  -v /dev/bus/usb:/dev/bus/usb \
  -v /dev/ttyACM0:/dev/ttyACM0 \
  ghcr.io/openrfstack/openrfstack-mobile:latest

# GPS serial mount is optional — omit if no GPS attached
# To run mobile standalone on 6443: add -e K3S_HTTPS_PORT=6443
# To run both on the same host simultaneously, no extra flags needed
4

Override devices.xml (SDR hardware config)

Both images ship a default devices.xml configured for PlutoSDR with auto-discovery (empty <uri>). Mount a custom config at runtime to change SDR type or address:

# Bind-mount your own devices.xml
sudo podman run -d --name sdr-node --network host --privileged \
  -v sdr-k3s:/var/lib/rancher/k3s \
  -v /dev/bus/usb:/dev/bus/usb \
  -v /etc/sdr/devices.xml:/etc/sdr/devices.xml:ro \
  ghcr.io/openrfstack/openrfstack-node:latest

<!-- devices.xml URI field — three valid forms: -->
<device id="pluto-0">
  <driver>plutosdr</driver>
  <uri></uri>                  <!-- empty  → USB auto-discovery (recommended) -->
  <!-- <uri>ip:192.168.2.1</uri>  → Ethernet-connected PlutoSDR          -->
  <!-- <uri>usb:1.7.5</uri>       → specific USB bus.port.device          -->
</device>
Do not set <uri>driver=plutosdr</uri>. That is a SoapySDR arg string, not a libiio URI — SoapyPlutoSDR will reject it and fail to open the device.
5

GPS serial passthrough (sdr-mobile)

GpsApp reads NMEA sentences directly from a serial port inside the container — no host gpsd needed. Find your GPS device node and bind-mount it:

ls /dev/ttyACM* /dev/ttyUSB*   # identify the GPS port

# Pass it in at launch (remap to /dev/ttyACM0 if different)
sudo podman run -d --name sdr-mobile --network host --privileged \
  -v sdr-mobile-k3s:/var/lib/rancher/k3s \
  -v /dev/bus/usb:/dev/bus/usb \
  -v /dev/ttyUSB0:/dev/ttyACM0 \
  ghcr.io/openrfstack/openrfstack-mobile:latest

Docker Compose Setup

1

Clone all repositories

All repos must be siblings — the build system uses relative paths (../SdrSdk, ../SdrTaskApi).

mkdir openrfstack && cd openrfstack
for repo in SdrSdk SdrTaskApi SdrResourceManager AcquisitionApp \
            DemodApp AnalysisApp SpeechApp SdrScripts; do
  git clone --branch main/1.0 https://github.com/OpenRFStack/$repo.git
done
2

Configure environment variables

# .env — place next to docker-compose.yml
AMQP_HOST=artemis
AMQP_PORT=5672
AMQP_USER=openrf
AMQP_PASS=changeme
POSTGRES_USER=openrf
POSTGRES_PASSWORD=changeme
POSTGRES_DB=openrfstack
MODEL_PATH=/models/amr_cnn_v1_47class.onnx
3

docker-compose.yml

services:

  artemis:
    image: apache/activemq-artemis:2.31.2
    environment:
      ARTEMIS_USER: ${AMQP_USER}
      ARTEMIS_PASSWORD: ${AMQP_PASS}
    ports: ["5672:5672", "8161:8161"]

  postgres:
    image: postgres:15-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: ${POSTGRES_DB}
    volumes: [pg_data:/var/lib/postgresql/data]

  sdr_resource_manager:
    build: ./SdrResourceManager
    devices: ["/dev/bus/usb:/dev/bus/usb"]   # USB SDR passthrough
    privileged: true
    depends_on: [artemis]

  acquisition:
    build: ./AcquisitionApp
    depends_on: [artemis, sdr_resource_manager]
    volumes: [./AcquisitionApp/config:/config:ro]

  demod:
    build: ./DemodApp
    depends_on: [artemis]

  analysis:
    build: ./AnalysisApp
    deploy:
      resources:
        reservations:
          devices: [{driver: nvidia, count: 1, capabilities: [gpu]}]
    volumes:
      - ./models:/models:ro
      - ./AnalysisApp/config:/config:ro
    depends_on: [artemis]

  speech:
    build: ./SpeechApp
    depends_on: [artemis]

volumes:
  pg_data:
4

Initialize the database schema

docker compose up -d postgres
docker compose exec postgres psql -U openrf openrfstack \
  -f /docker-entrypoint-initdb.d/init.sql
# Or mount AcquisitionApp/schema/init.sql as initdb script
5

Start the full stack

docker compose up -d
docker compose logs -f acquisition demod analysis

# Artemis management UI: http://localhost:8161 (admin/changeme)
# PostgreSQL:            localhost:5432

Configuration Reference

Each app reads its config from an XML file. Mount the config directory as a read-only volume. The most important knobs for initial setup: 
<!-- AcquisitionApp/config/scanner.xml — key fields -->
<sdr_acquisition>
  <scanner_id>scanner-0</scanner_id>

  <amqp>
    <url>amqp://artemis:5672</url>
    <username>openrf</username>
    <password>changeme</password>
  </amqp>

  <device>
    <sample_rate_sps>10000000</sample_rate_sps>
    <rx_gain_db>40</rx_gain_db>
  </device>

  <!-- Shared sweep defaults (FFT size, threshold, CFAR, etc.) -->
  <sweep>
    <start_hz>70000000</start_hz>
    <stop_hz>6000000000</stop_hz>
    <fft_size>4096</fft_size>
    <threshold_db>10.0</threshold_db>
  </sweep>

  <!-- Optional: explicit band plan. AcquisitionApp queries SdrRM for online   -->
  <!-- device count at startup and auto-splits bands so each device gets a      -->
  <!-- unique non-overlapping slice. With 4 PlutoSDRs and 2 bands each band     -->
  <!-- is split into 2 equal slices (4 total). Omit <bands> to treat the full   -->
  <!-- <sweep> range as one band and split it across all available devices.     -->
  <bands>
    <band><start_hz>70000000</start_hz><stop_hz>1100000000</stop_hz></band>
    <band><start_hz>1100000000</start_hz><stop_hz>6000000000</stop_hz></band>
  </bands>

  <threat>
    <enabled>true</enabled>
    <gps_enabled>true</gps_enabled>
    <adsb_enabled>true</adsb_enabled>
    <ais_enabled>true</ais_enabled>
    <eas_enabled>true</eas_enabled>
    <p25_rogue_enabled>true</p25_rogue_enabled>
  </threat>
</sdr_acquisition>

Common Issues

!

SoapySDR device not found in container

The container needs access to /dev/bus/usb and the udev rules must run on the host before the container starts. Verify with:

docker run --rm --privileged -v /dev/bus/usb:/dev/bus/usb \
  openrfstack/sdr_resource_manager SoapySDRUtil --find
!

AMQP connection refused at startup

Apps retry on connection failure, but Artemis can take 10–15 s to be ready. Add a healthcheck or use depends_on: condition: service_healthy in Compose. Artemis health endpoint: http://artemis:8161/console/jolokia/read/org.apache.activemq.artemis:broker=*/Started

!

AnalysisApp: CUDA OOM

Reduce batch_size in analysis.xml. The v1 model (47-class, 128ch) needs ~62 MB VRAM. With batch_size=256 and other processes sharing the GPU, 4 GB cards may OOM. Reduce to 64 or 32:

<inference batch_size="32" confidence_threshold="0.65"/>
!

PlutoSDR: device not found / sample drops

Leave <uri></uri> empty in devices.xml — SoapyPlutoSDR then auto-discovers via USB scan. The <uri> field is a libiio URI (ip:192.168.2.1 or usb:1.7.5), not a SoapySDR driver hint; setting it to driver=plutosdr will cause "no device context found". For Ethernet-connected PlutoSDR use <uri>ip:192.168.2.1</uri> — no USB bandwidth limit, both RX channels at full rate. For USB-only: leave empty or pin to a specific bus/port with usb:1.7.5 (find with SoapySDRUtil --find=driver=plutosdr). Always use --network host in containers so libiio USB contexts resolve correctly. Limit sample_rate_sps to 4 000 000 for USB-only PlutoSDR to avoid USB bandwidth drops.

!

pqxx demangle_type_name linker error

Occurs when libpqxx 7.x is paired with std::optional<T> in the same translation unit. The AlertStore uses a pimpl pattern and manually-built SQL strings to avoid this — do not include <pqxx/pqxx> in any header that is also included by a TU that includes <nlohmann/json.hpp>.
